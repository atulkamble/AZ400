# Jenkins CI/CD Setup Guide — Linux and Windows

> Last reviewed: July 2026  
> Recommended Jenkins runtime: **Java 21**  
> Default Jenkins port: **8080**

---

## 1. Jenkins Overview

**Jenkins** is an open-source automation server used to automate software build, test, integration, delivery, and deployment activities.

### CI — Continuous Integration

Continuous Integration automatically:

1. Pulls source code from a remote Git repository.
2. Builds the application.
3. Runs tests and quality checks.
4. Reports errors quickly.
5. Produces deployable artifacts or container images.

### CD — Continuous Delivery / Continuous Deployment

- **Continuous Delivery:** The application is always ready for release, but production deployment may require manual approval.
- **Continuous Deployment:** Every approved and successful change can be deployed automatically to production.

### Jenkins and Azure DevOps

| Service | Purpose |
|---|---|
| Jenkins | Open-source CI/CD automation server |
| Azure Pipelines | Microsoft-hosted or self-hosted CI/CD pipeline service |
| Azure DevOps | Platform for Boards, Repos, Pipelines, Test Plans, and Artifacts |
| GitHub Actions | GitHub-native workflow and CI/CD automation |

## 2. SDLC and Environment Flow

**SDLC** stands for **Software Development Life Cycle**.

A common software delivery flow is:

```text
Plan
  ↓
Develop
  ↓
Build
  ↓
Test
  ↓
Development Environment
  ↓
Staging / UAT Environment
  ↓
Production / Release
  ↓
Website / Web App / Mobile App / API
```

### Why CI/CD?

- Minimizes release time
- Reduces repetitive manual work
- Improves build consistency
- Detects errors earlier
- Automates testing and deployment
- Integrates multiple DevOps tools
- Supports frequent and reliable releases

### Common Jenkins Integrations

```text
Git / GitHub / GitLab / Azure Repos
                ↓
             Jenkins
                ↓
      Maven / Gradle / npm / Python
                ↓
             Testing
                ↓
              Docker
                ↓
       Kubernetes / Cloud / VM
```

## 9. Install Jenkins LTS on Ubuntu

Create the keyring directory if it does not already exist:

```bash
sudo mkdir -p /etc/apt/keyrings
```

Install `wget`:

```bash
sudo apt install wget -y
```

Add the Jenkins LTS repository key:

```bash
sudo wget -O /etc/apt/keyrings/jenkins-keyring.asc \
  https://pkg.jenkins.io/debian-stable/jenkins.io-2026.key
```

Add the Jenkins repository:

```bash
echo "deb [signed-by=/etc/apt/keyrings/jenkins-keyring.asc]" \
  https://pkg.jenkins.io/debian-stable binary/ | sudo tee \
  /etc/apt/sources.list.d/jenkins.list > /dev/null
```

Install Jenkins:

```bash
sudo apt update
sudo apt install jenkins -y
```

Check the installed version:

```bash
jenkins --version
```

Alternative:

```bash
dpkg -s jenkins | grep Version
```

```bash

```

```bash

```

```bash

```

Restart Jenkins:

```bash
sudo systemctl restart jenkins
```

Test Docker as the current user:

```bash
docker images
```

Test Docker as Jenkins:

```bash
sudo -u jenkins docker version
```

> Membership in the Docker group provides privileged access to the Docker daemon. Use it carefully on production systems.

## 21. Windows Installation Method 1 — MSI Installer

The Windows MSI installer is the recommended method for a permanent Jenkins controller.

1. Download the latest Jenkins **LTS Windows installer** from the official Jenkins download page.
2. Run the `.msi` file as Administrator.
3. Select the installation directory.
4. Configure the Jenkins service account.
5. Use a dedicated local or domain service account for production.
6. Select Java 21 when prompted.
7. Keep the default port `8080`, or select another available port.
8. Complete the installation.
9. Verify that the **Jenkins** Windows service is running.

Check the service:

```powershell
Get-Service Jenkins
```

Start or restart it:

```powershell
Start-Service Jenkins
Restart-Service Jenkins
```

Open Jenkins:

```text
http://localhost:8080
```

For a remote Azure VM:

```text
http://<public-ip>:8080
```

### Initial password for MSI installation

The setup wizard displays the password location. A common default location is:

```text

```

Display it from PowerShell:


## 23. Windows Installation Method 3 — WAR File

Use the WAR method for local practice, testing, or a temporary Jenkins instance.

Create a Jenkins folder:

```powershell
New-Item -ItemType Directory -Path C:\Jenkins -Force
Set-Location C:\Jenkins
```

Download the Jenkins LTS WAR file:

```powershell
Invoke-WebRequest `
  -Uri "https://get.jenkins.io/war-stable/latest/jenkins.war" `
  -OutFile "C:\Jenkins\jenkins.war"
```

Run Jenkins:

```powershell
java -jar C:\Jenkins\jenkins.war
```

Run on a custom port:

```powershell

```

Open:

```text

```

The password is normally displayed in the console.

You can also check:

```powershell

```

> When Jenkins is started using `java -jar`, closing the terminal stops Jenkins. Use the MSI installation when Jenkins must run permanently as a Windows service.

```groovy
    }
```

5. Select **OK**.
6. In the **Pipeline** section, configure:

```text

```

7. Select **Save**.
8. Select **Build Now**.
9. Open **Console Output**.

### Repository Jenkinsfile

The current repository Jenkinsfile uses the branch name as the Docker tag:

```groovy
pipeline {
    agent any

    environment {
        IMAGE_TAG = "${env.BRANCH_NAME?.replaceAll('/', '-') ?: 'latest'}"
    }

    stages {
        stage('Docker Build') {
            steps {
                echo "Building Docker image with tag: app:${IMAGE_TAG}"
                sh "docker build -t app:${IMAGE_TAG} ."
            }
        }
    }
}
```

### Behavior

For a standard single-branch Pipeline job, `BRANCH_NAME` may not be available, so the image tag falls back to:

```text
app:latest
```

For a Multibranch Pipeline, Jenkins automatically provides `BRANCH_NAME`.

Examples:

| Git branch | Docker image |
|---|---|
| `main` | `app:main` |
| `dev` | `app:dev` |
| `feature/login` | `app:feature-login` |

The slash in `feature/login` is replaced with a hyphen because Docker tags cannot safely use the Git branch name unchanged.

## 37. Recommended Expanded Jenkinsfile for the Repository

Use this example to add checkout, validation, Docker build, and image verification.

```groovy
pipeline {
    agent any

    environment {
        APP_NAME = 'mypipeline'
    }

    stages {
        stage('Prepare') {
            steps {
                script {
                    env.SAFE_BRANCH = (env.BRANCH_NAME ?: 'main')
                        .replaceAll('[^A-Za-z0-9_.-]', '-')
                        .toLowerCase()

                    env.IMAGE_TAG = "${env.SAFE_BRANCH}-${env.BUILD_NUMBER}"
                }

                echo "Branch: ${env.BRANCH_NAME ?: 'single-pipeline-job'}"
                echo "Image: ${APP_NAME}:${IMAGE_TAG}"
            }
        }

        stage('Checkout') {
            steps {
                checkout scm
            }
        }

        stage('Validate Python') {
            steps {
                sh 'python3 -m py_compile app.py'
            }
        }

        stage('Docker Build') {
            steps {
                sh 'docker build -t ${APP_NAME}:${IMAGE_TAG} .'
            }
        }

        stage('Verify Image') {
            steps {
                sh 'docker image inspect ${APP_NAME}:${IMAGE_TAG}'
            }
        }
    }

    post {
        success {
            echo "Pipeline successful: ${APP_NAME}:${IMAGE_TAG}"
        }

        failure {
            echo 'Pipeline failed. Check Console Output.'
        }

        cleanup {
            cleanWs()
        }
    }
}
```

### Image-tag examples

```text
mypipeline:main-12
mypipeline:dev-13
mypipeline:feature-login-14
```

Using both the branch and Jenkins build number avoids overwriting every build with the same tag.

> The `cleanWs()` step requires the Workspace Cleanup plugin. Remove the `cleanup` block when that plugin is not installed.

## 38. Multibranch Pipeline Overview

A **Multibranch Pipeline** automatically discovers Git branches that contain a `Jenkinsfile`.

Example:

```text
GitHub Repository
├── main
│   └── Jenkinsfile
├── dev
│   └── Jenkinsfile
└── feature/login
    └── Jenkinsfile
          ↓
Jenkins Multibranch Pipeline
├── main pipeline
├── dev pipeline
└── feature-login pipeline
```

### Advantages

- Automatically discovers branches
- Runs an independent Pipeline for each branch
- Provides the `BRANCH_NAME` environment variable
- Supports branch-specific stages
- Supports feature-branch validation
- Can discover pull requests when GitHub Branch Source is configured
- Removes or disables jobs when branches are deleted, depending on orphaned-item settings

## 41. Branch-Specific Multibranch Jenkinsfile

The following Pipeline applies different behavior to feature, development, and main branches.

```groovy
pipeline {
    agent any

    environment {
        APP_NAME = 'mypipeline'
    }

    stages {
        stage('Prepare') {
            steps {
                script {
                    env.SAFE_BRANCH = (env.BRANCH_NAME ?: 'main')
                        .replaceAll('[^A-Za-z0-9_.-]', '-')
                        .toLowerCase()

                    env.IMAGE_TAG = "${env.SAFE_BRANCH}-${env.BUILD_NUMBER}"
                }

                echo "Running branch: ${BRANCH_NAME}"
                echo "Building image: ${APP_NAME}:${IMAGE_TAG}"
            }
        }

        stage('Checkout') {
            steps {
                checkout scm
            }
        }

        stage('Validate') {
            steps {
                sh 'python3 -m py_compile app.py'
            }
        }

        stage('Docker Build') {
            steps {
                sh 'docker build -t ${APP_NAME}:${IMAGE_TAG} .'
            }
        }

        stage('Feature Branch Validation') {
            when {
                expression {
                    env.BRANCH_NAME?.startsWith('feature/')
                }
            }

            steps {
                echo 'Feature branch: build and validation only.'
            }
        }

        stage('Deploy to Development') {
            when {
                branch 'dev'
            }

            steps {
                echo 'Deploying the dev branch to the development environment.'
            }
        }

        stage('Production Approval') {
            when {
                branch 'main'
            }

            steps {
                input message: 'Deploy the main branch to production?',
                      ok: 'Deploy'
            }
        }

        stage('Deploy to Production') {
            when {
                branch 'main'
            }

            steps {
                echo 'Deploying the main branch to production.'
            }
        }
    }

    post {
        success {
            echo "Successful branch build: ${BRANCH_NAME}"
        }

        failure {
            echo "Failed branch build: ${BRANCH_NAME}"
        }

        always {
            echo "Completed Jenkins build number ${BUILD_NUMBER}"
        }
    }
}
```

### Branch flow

```text
feature/*
   └── Checkout → Validate → Docker Build → Feature Validation

dev
   └── Checkout → Validate → Docker Build → Deploy to Development

main
   └── Checkout → Validate → Docker Build
       → Production Approval → Deploy to Production
```

> The deployment steps above use `echo` for safe practice. Replace them with real deployment commands only after credentials, approvals, rollback, and environment protections are configured.

## 42. GitHub Webhook for Automatic Jenkins Builds

A webhook tells Jenkins when code is pushed to GitHub.

### Jenkins job configuration

For a normal Pipeline job, enable:

```text
Build Triggers
  → GitHub hook trigger for GITScm polling
```

For a Multibranch Pipeline, use GitHub Branch Source and webhook-based branch indexing when available.

### GitHub configuration

Open the repository:

```text
Settings
  → Webhooks
  → Add webhook
```

Configure:

```text
Payload URL: https://<jenkins-domain>/github-webhook/
Content type: application/json
SSL verification: Enabled
Events: Just the push event
Active: Enabled
```

For a temporary HTTP lab:

```text
http://<jenkins-public-ip>:8080/github-webhook/
```

The trailing slash in `/github-webhook/` is important.

### Azure NSG consideration

When Jenkins port `8080` is allowed only from **My IP**, GitHub cannot reach the webhook endpoint.

For a lab, use one of these approaches:

1. Use **Scan Multibranch Pipeline Now** manually.
2. Enable periodic Multibranch scanning.
3. Securely expose Jenkins through an HTTPS reverse proxy.
4. Allow webhook traffic only through an appropriately secured network design.

Do not expose an administrative Jenkins controller directly to the internet for production use.

## 43. GitHub Credentials for a Private Repository

A public repository can normally be cloned without Jenkins credentials.

For a private repository:

1. Open:

```text
Manage Jenkins
  → Credentials
  → System
  → Global credentials
  → Add Credentials
```

2. For HTTPS authentication, configure an appropriate GitHub token credential.

Example credential information:

```text
Kind: Username with password
Username: GitHub username
Password: GitHub personal access token
ID: github-credentials
Description: GitHub repository access
```

3. Select `github-credentials` in the Pipeline or Multibranch job.

Never store a token directly inside:

```text
Jenkinsfile
README.md
Dockerfile
Shell script
Git repository
```

## 45. Pipeline Troubleshooting

### Jenkins reports `Jenkinsfile not found`

Check:

```text
Script Path: Jenkinsfile
```

The filename is case-sensitive on Linux:

```text
Correct: Jenkinsfile
Incorrect: jenkinsfile
Incorrect: JenkinsFile
```

Confirm the file exists in the branch Jenkins is building.

### Branch is not displayed in the Multibranch job

1. Select **Scan Multibranch Pipeline Now**.
2. Check **Scan Multibranch Pipeline Log**.
3. Confirm the branch was pushed to GitHub.
4. Confirm the branch contains a `Jenkinsfile`.
5. Check branch discovery behaviors.
6. Check repository credentials.

### `BRANCH_NAME` is empty

`BRANCH_NAME` is normally provided by a Multibranch Pipeline.

For a standard Pipeline job, use a fallback:

```groovy
env.BRANCH_NAME ?: 'main'
```

### Git checkout fails

Verify:

```bash
git ls-remote https://github.com/atulkamble/mypipeline.git
```

Check:

- Git is installed on the Jenkins agent.
- Repository URL is correct.
- Credentials are correct for a private repository.
- Jenkins can access GitHub over HTTPS.

### Docker permission denied on Linux

```bash
sudo usermod -aG docker jenkins
sudo systemctl restart docker
sudo systemctl restart jenkins
sudo -u jenkins docker version
```

### `docker: command not found`

```bash
docker --version
which docker
```

Confirm Docker is installed on the Jenkins node that runs the Pipeline.

### `python3: command not found`

```bash
sudo apt install python3 -y
python3 --version
```

On Windows, use:

```groovy
bat 'python --version'
```

### Docker image tag is invalid

Sanitize branch names:

```groovy
env.BRANCH_NAME
    .replaceAll('[^A-Za-z0-9_.-]', '-')
    .toLowerCase()
```

### Webhook does not trigger Jenkins

Check:

1. The webhook URL ends in `/github-webhook/`.
2. GitHub shows a successful delivery.
3. Jenkins is reachable from GitHub.
4. The correct trigger is enabled.
5. The GitHub and GitHub Branch Source plugins are installed.
6. HTTPS certificates are valid.
7. Azure NSG and firewall rules allow the required traffic.
